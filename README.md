# Selaras SaaS Starter

A Nuxt 4.6 SaaS workspace starter built with the published `@sewadah/selaras` package. A compact application rail, workspace sidebar, project tabs, central work area, right inspector, and bottom status bar give every part of the application a clear place.

## Quick start

Scaffold a new project from the `master` branch of this template. Nuxt will ask where to create it:

```sh
npm create nuxt@latest -- -t github:sewadahapp/selaras-saas#master
```

In the generated project, install dependencies and start the development server with your preferred package manager:

```sh
npm install
npm run dev
```

Open `http://localhost:3000`. You can also use `bun install` / `bun run dev`, `pnpm install` / `pnpm dev`, or `yarn` / `yarn dev`.

## Develop this repository

Clone the starter to contribute to it directly:

```sh
git clone --branch master git@github.com:sewadahapp/selaras-saas.git
cd selaras-saas
npm install
npm run dev
```

Node.js 24 is the contributor and CI default (`.nvmrc`). The repository includes `bun.lock`, but `package.json` does not pin a package manager or runtime. You can use npm, pnpm, Yarn, or Bun; keep the lockfile generated by your chosen package manager.

The package is named `selaras-saas`. It is a reusable Nuxt application template, so `private: true` prevents accidental publication to npm without affecting scaffolding from GitHub. Styles use Tailwind CSS 4 and ordinary CSS.

## Included screens

| Route       | Screen                                                                                                |
| ----------- | ----------------------------------------------------------------------------------------------------- |
| `/`         | Project overview, document previews, live task progress, upcoming tasks, latest update                |
| `/tasks`    | Search, status filter, task creation, completion, and task inspector                                  |
| `/files`    | Three sample Markdown documents with previews and working downloads                                   |
| `/activity` | Project activity, including newly created tasks and status changes                                    |
| `/settings` | Workspace name, dark mode, and confirmed demo reset                                                   |
| `/inbox`    | App-wide inbox with search, All/Unread/Starred/Archive/Sent/Trash views, reader, replies, and compose |
| `/chats`    | Channels and direct conversations, message history, per-conversation drafts, and message composer     |

The application rail switches between **Workspace**, **Inbox**, and **Chats**. Workspace keeps project navigation, tasks, files, and activity in its sidebar and tabs. Inbox replaces that sidebar with a message list and filters; Chats replaces it with channels and direct conversations. The communication screens use a list and content pane instead of showing project navigation or a project inspector.

The rail uses Selaras `SNavigationMenu` in vertical collapsed mode for application sections, search, settings, and account access. The library provides keyboard navigation, active styling, accessible hidden labels, and right-side tooltips. Unread counts and the account avatar use the menu's trailing and leading slots.

Switch between the sample projects in the workspace sidebar, or create your own. Every project's tasks, progress, and activity are isolated. New tasks are assigned to the demo account. Click a task name to open its details and change its status. A completed task can be reopened with its checkbox or inspector.

Search (`Cmd/Ctrl K`) uses Selaras's command palette to navigate screens and switch projects. Appearance uses Selaras's color mode controls. All interactive controls use Selaras components, including `SSelect` for priority, task filtering, and task status; `SButton` for actions; `SNavigationMenu` for rail/sidebar navigation; and `STabs` for project views and inbox filters. `SDashboardNavbar` supplies header bars, `SPageHeader` supplies page headings, `STimeline` supplies activity feeds, and `SToolbar`/`SToolbarButton` supply email actions. Cards, avatars, avatar groups, breadcrumbs, empty states, forms, checkboxes, dialogs, slideovers, progress bars, badges, and notifications also use Selaras. `SDashboardGroup`, `SDashboardSidebar`, `SDashboardResizeHandle`, and `SDashboardPanel` manage the desktop split panels. The outer grid keeps the application rail and bottom status bar separate. Starter components compose these primitives with workspace behavior; they do not recreate UI controls.

## Layout

- **Left rail:** application navigation, search, appearance, and account/settings.
- **Sidebar:** resizable workspace navigation, project selection, project creation, and a starter resource card. Settings and account access live in the rail.
- **Top tabs:** `STabs` with URL-backed Overview, Tasks, Files, and Activity panels, the library's animated indicator, keyboard navigation, and overflow scrolling.
- **Main:** independent scrolling, keeping navigation and the status bar stationary.
- **Right inspector:** resizable project properties, progress, team, and activity. Task selection reveals the inline inspector on desktop, or a right slideover on smaller screens. The task's close button returns to project details.
- **Bottom bar:** local save status, quick search shortcut, and help link.

At 1200 px and above, all columns are available. Drag either divider or focus it and use the arrow keys to resize. The workspace sidebar starts at 240 px and resizes from 200–360 px; the inspector starts at 280 px and resizes from 220–400 px. Header buttons independently collapse each panel to zero width and restore its previous width. Panels stay mounted and use Selaras's built-in 200 ms transition, with reduced motion respected.

The inspector has its own nested dashboard group so its toggle and saved size are independent of the workspace sidebar. Each group saves its layout in a separate cookie: `selaras-sass-navigation-v1` and `selaras-sass-inspector-v1`. Collapsed state and the width to restore survive reloads. Keep the sidebar collapse props uncontrolled so the library owns that persistence.

The route determines the active project tab. Selecting a tab changes its URL, and direct links, reloads, and browser history select the matching tab. Each active tab panel contains `WorkspacePageContent.vue` and the routed page; inactive routed content unmounts. Tab triggers, indicators, colors, and typography retain the Selaras defaults. Tab UI overrides only arrange the panel and its scrolling content.

Custom presentation code is limited to application layout and content: file-preview artwork, task-row composition, chat-message alignment, message summaries, and page spacing. Those compositions use Selaras controls, cards, badges, and avatars. Ordinary headings within content, links, lists, and semantic containers remain HTML.

The workspace sidebar uses the dashboard component's header and footer slots: workspace identity stays at the top, the starter card stays at the bottom, and navigation scrolls between them. The application rail owns the single Selaras logo, settings link, and account avatar. The mobile drawer uses the same header/footer components. The optional starter card hides on short viewports to preserve room for navigation. `SelarasLogo.vue` uses the light/dark wordmarks and favicon from the dashboard starter; paths respect Nuxt's base URL, including GitHub Pages project paths.

Below 1200 px, the right inspector is available from the header's details button. Below 768 px, workspace navigation also becomes a slideover. The application rail, project tabs, and status bar remain available. Desktop panels remain mounted but are hidden at these breakpoints. The dashboard groups use `mobile-breakpoint="0"` to retain their splitter state; explicit Selaras `SSlideover` components provide the left and right overlays, since this version of `SDashboardSidebar` fixes its own mobile drawer to the left edge.

Inbox and Chats each have a resizable `SDashboardSidebar` for their lists, starting at 340 px with limits of 280–480 px. Each list has its own layout cookie. Below 768 px, choosing a message or conversation switches from the list to its content; the back button returns to the list. Selected items have bookmarkable URLs, such as `/inbox?mail=homepage` and `/chats?chat=studio`. The rail remains available in both views.

The chat header's members button toggles a right `SDashboardSidebar`. It starts closed, expands with Selaras's built-in transition, and resizes from 240–400 px. A separate dashboard group keeps its width independent of the conversation list. Below 1200 px, the same member list opens in a right `SSlideover`. The list follows the selected conversation and closes when leaving Chats.

## Demo data and persistence

Projects, tasks, workspace name, active project, and activity are saved in this browser under `selaras-sass:v1`. The composable loads storage after mounting so server rendering and hydration start with the same data. Storage failures fall back to session state with a visible notice. Invalid saved data is preserved, and automatic writes stay disabled until you explicitly reset the demo in Settings.

The files and team are static starter examples. Documents use the selected project's name in downloaded Markdown. The team is display data; there is no invitation or membership backend.

This starter has no authentication, server database, collaborative synchronization, billing, or file upload service. **Pro** is a demo plan label. Connect your own backend at `app/composables/useWorkspace.ts` and enforce access on the server when adding real accounts and data.

Inbox and Chats are local demonstrations. Messages, replies, sent emails, conversation history, read state, stars, and drafts persist separately under `selaras-sass:communications:v1`. Sending a reply or composing a message does **not** send real email; chat messages are saved only in this browser, without simulated incoming replies. Connect an email or messaging service at `app/composables/useCommunications.ts` for production behavior.

Unread badges in the rail reflect the actual demo messages. Opening a message marks it read; it can be marked unread again. Archive and trash actions retain messages, and the reader can restore them to the inbox. Search covers sender, recipient, subject, and body. Each conversation keeps its own draft; `Cmd/Ctrl Enter` submits the chat composer. New direct conversations reuse an existing conversation with that teammate. A confirmed **Reset demo** action restores communication examples without changing projects or tasks. The workspace reset in Settings keeps communication data. Invalid saved communication data is preserved until the explicit message reset.

## Commands and checks

```sh
npm run dev          # Development server
npm run lint         # ESLint
npm run typecheck    # Nuxt and Vue types
npm run build        # Production SSR build
npm run generate     # Static output in .output/public
npm run preview      # Preview production build
bun run test         # Workspace validation and progress tests
bun run check        # Lint, types, unit tests, and production build
```

The unit test and `check` scripts require Bun. Other scripts work with your preferred package manager.

Browser tests cover navigation, desktop/mobile shells, pointer and keyboard resizing, independent sidebar collapse, restored layout cookies, responsive slideovers, task creation and persistence, project isolation, document downloads, and corrupt storage recovery. Communication checks cover rail/context switching, reply and chat drafts, sent messages, archive/read/star behavior, conversation isolation, and mobile navigation. To run them:

```sh
npx playwright install chromium
npm run build
npm run test:e2e
```

Playwright starts the production server on port 3020. Set `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` if you want to use an existing Chromium installation. The GitHub Actions validation workflow installs its browser and runs the checks.

## Deploy

For Node hosting, run `npm run build`, then `node .output/server/index.mjs`. Set `NITRO_HOST` and `NITRO_PORT` as needed.

For static hosting, run `npm run generate` and deploy `.output/public`. The included GitHub Pages workflow runs lint, type checks, unit tests, a production build, and desktop/mobile browser tests before generating and publishing static output after a merge or push to `master`. It configures the repository base path automatically. Enable **Settings → Pages → Build and deployment → Source → GitHub Actions** in your own repository. For a project generated from this starter, update the workflow branch if you use a default branch other than `master`. Remove the workflow if using a different host.
